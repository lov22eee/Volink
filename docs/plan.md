## 1. 작품 배경

### 1.1 봉사를 시작하기 어려운 이유

자원봉사에 관심이 있어도 실제 참여로 이어지지 않는 경우가 많다. 「2026 대한민국 내셔널 자원봉사 리포트」에 따르면, 관심이 생겨 정보를 찾아봤지만 참여하지 않은 응답자의 47.8%가 ‘참여할 수 있는 시간대의 활동이 없어서’, 21.2%가 ‘시간이 오래 걸리는 활동밖에 없어서’라고 답했다. 관심 자체를 갖지 않은 응답자에서도 1위 이유는 ‘시간 여유 부족’(48.7%)이었다.

20~24세에서는 이 차이가 더 분명하다. 2023년 사회조사에서 20~24세의 향후 1년 내 참여 의향은 29.3%였지만, 지난 1년 동안 실제로 참여한 비율은 12.1%에 그쳤다. 즉 봉사할 마음이 없어서라기보다 ‘내 시간과 동선에 맞는 짧은 활동을 찾기 어렵다’는 점이 참여를 막는 주요 원인으로 볼 수 있다.

### 1.2 기존 방식에서 반복되는 문제

사례 1은 지역 문제를 발견해도 이를 바로 활동으로 만들 방법이 없는 경우다. 공식 포털은 기관·단체가 등록한 활동에 참여하는 구조가 중심이어서, ‘이번 주말, 우리 동네’처럼 조건이 좁아지면 맞는 활동을 찾기 어렵다.

사례 2는 커뮤니티 글과 오픈채팅으로 사람을 모은 경우다. 모집은 쉽지만 연락처가 노출되고, 누가 확정 인원인지와 실제로 왔는지가 기록되지 않아 다음 활동으로 이어지기 어렵다. 두 사례 모두 모집 이후의 관리(정원·대기·출석·기록)가 비어 있다는 공통점이 있다.

### 1.3 문제와 해결방향

본 작품은 주민이 생활권에서 발견한 작은 문제를 2~10명, 3시간 이내의 활동으로 직접 만들고, 가까운 사람을 모아 실제 활동과 기록까지 이어지게 하는 웹 플랫폼을 만드는 것을 목적으로 한다. 모집 글을 올리는 기능보다 정원·대기·체크인·완료라는 참가 상태를 서버가 규칙대로 관리하는 것에 집중한다.

또한 모르는 사람끼리 만나는 활동이므로 안전 문제가 생길 수 있다. 위험 가능성이 있는 활동은 게시 전에 걸러내고, 문제가 생기면 신고와 관리자 조치 기록을 남긴다. 플랫폼이 사실관계를 확정할 수 없는 문제는 한쪽 주장으로 결론 내리지 않고 해당 기록을 보류한다.

| 관찰된 문제 | 설계 방향 |
|---|---|
| 맞는 시간대의 활동이 없음 | 누구나 2~10명, 3시간 이내 활동을 직접 개설 |
| 가까운 활동을 찾기 어려움 | 활동 장소를 좌표로 저장하고 반경·날짜·분야로 검색 |
| 오픈채팅 모집 시 연락처 노출 | 플랫폼 안에서 신청·승인·알림, 연락처 비공개 |
| 누가 확정 인원인지 혼선 | 정원 확정을 서버에서 잠그고, 초과 신청은 대기 순번 부여 |
| 취소가 나도 빈자리가 방치됨 | 대기 1순위에게 자동 승격 제안, 응답 제한시간이 지나면 다음 순번 |
| 실제로 왔는지 알 수 없음 | 시간·QR·위치를 함께 확인하는 현장 체크인 |
| 위험한 활동이 모집될 가능성 | 게시 전 위험도 검사(LOW·REVIEW·BLOCKED)와 관리자 검토 |
| 활동이 한 번으로 끝남 | 개인 활동 기록 누적, 일정 여유 시 크루로 반복 활동 연결 |

## 2. 작품 주제

### 2.1 서비스 개요

모집자는 활동명·일시·장소·정원을 한 번 등록하고, 서버는 게시 전에 위험도를 검사한다. 참가자는 지도와 목록에서 가까운 활동을 찾아 신청하고, 모집자가 승인하면 정원 안에서 참가가 확정된다. 정원이 차면 대기 순번을 받고, 빈자리가 생기면 순서대로 참가 제안을 받는다. 활동 당일에는 시간·QR·위치를 함께 확인해 체크인하고, 모집자의 완료 확인으로 활동 기록이 만들어진다.

### 2.2 핵심 기능

| 기능 | 내용 |
|---|---|
| ① 위치 기반 소규모 활동 개설·탐색 | 활동 장소를 좌표로 저장하고, 참가자는 반경·날짜·분야로 가까운 활동을 검색한다. 활동은 2~10명, 3시간 이내로 제한한다. |
| ② 정원 확정과 대기열 자동 승격 | 승인 시 서버가 정원을 잠가 초과 확정을 막는다. 취소가 생기면 대기 1순위에게 제한시간 안에 수락하도록 자동으로 제안한다. |
| ③ 현장 체크인 | 모집자 화면에 60초마다 바뀌는 QR을 표시하고, 체크인 시 시간·QR·위치(반경 200m)를 함께 확인한다. |
| ④ 완료 확인과 활동 기록 | 체크인한 참가자만 모집자 완료 확인 대상이 되며, 확인 즉시 개인 활동 기록이 생긴다. 참가자는 7일간 이의를 제기할 수 있다. |
| ⑤ 위험 활동 검사와 신고 처리 | 금지 규칙·키워드로 LOW·REVIEW·BLOCKED를 나누고, REVIEW는 관리자 승인 전까지 비공개로 둔다. 신고는 증빙과 함께 접수하고 조치 사유를 기록한다. |

### 2.3 작품이 제공하는 핵심 가치

참가자는 자기 시간과 동선에 맞는 짧은 활동을 찾고, 연락처를 공개하지 않고 신청한다. 모집자는 확정·대기·취소를 일일이 챙기지 않아도 서버가 정원과 순번을 관리한다. 활동 기록은 실제 체크인과 모집자 확인을 거친 경우에만 만들어진다.

사실관계를 확인할 수 없는 신고는 관리자가 한쪽 주장으로 결론 내리지 않고 해당 기록을 보류하며, 누가 언제 어떤 상태를 바꿨는지 기록으로 남긴다.

## 3. 시장 추세

### 3.1 자원봉사 참여 현황

행정안전부 「2026 대한민국 자원봉사 현황」에 따르면 2025년 1365 자원봉사포털 등록 인원은 1,580만 9,567명(인구 대비 30.9%)이지만, 실제로 1회 이상 활동한 인원은 220만 2,264명으로 등록자 대비 13.9%였다. 연인원 참여는 1,834만 명으로 전년보다 5.8% 늘었고, 활동 시간의 경제적 가치는 약 1조 6,276억 원으로 추산됐다.

사회조사 기준 자원봉사 경험률도 2019년 16.1%에서 코로나19 영향으로 2021년 8.4%까지 떨어졌다가 2025년 14.4%로 회복 중이다. 등록한 사람은 많지만 실제 활동으로 이어지는 비율이 낮다는 점에서, 참여 문턱을 낮추는 서비스가 필요하다고 판단했다.

2025년 사회조사에서 자원봉사에 참여한 이유 1위는 ‘학교·직장 등 소속 조직의 단체활동에 동참하기 위해서’(35.0%)였다. 사람들은 함께하자고 불러주는 모임이 있을 때 움직인다는 뜻이며, Volink는 기관이 아닌 개인도 이 ‘불러주는 사람’(모집자)이 될 수 있게 하는 데 초점을 둔다. 다만 이 수치가 본 서비스의 실제 수요를 직접 보장하지는 않는다.

### 3.2 정책 흐름과 제도적 한계

행정안전부의 「자원봉사활동 진흥을 위한 제4차 국가 기본 계획(2023~2027)」은 자원봉사 몰입 시간이 줄고 ‘마이크로 자원봉사’가 떠오르는 변화를 짚고, 시민 주도형·일상적 자원봉사 확대와 시간·공간적 참여 접근성 강화를 과제로 제시했다. 2026년 ‘세계 자원봉사자의 해’를 준비한 정책 연구에서도 생활밀착형 자원봉사 프로그램 확대가 실천 전략으로 제시됐다. 본 작품은 이 흐름에 맞춰 짧고 가까운 활동의 개설과 관리에 집중한다.

반면 자원봉사 종합 보험은 1365·VMS·DOVOL을 통해 참여한 활동에 적용되며, 포털을 거치지 않고 개별적으로 운영하는 활동은 지원하지 않는다. 따라서 Volink는 공공장소·주간·저위험 활동만 게시하도록 제한하고 보험 비적용 사실을 화면에 표시한다. 공식 실적이나 보험이 필요한 활동은 향후 기관 계정을 통해 1365에 등록하는 방식으로 확장할 수 있다.

### 3.3 기존 봉사활동 연결 비교

각 서비스의 공식 안내에서 확인되는 운영 목적을 기준으로 비교했다. 공개 안내에 없는 기능을 ‘없음’으로 단정하지 않고, 본 작품이 구현하고 검증할 범위를 구분한다.

| 구분 | 공식 자료에서 확인한 제공 방식 | 본 작품의 구현 초점 |
|---|---|---|
| 1365 자원봉사포털 | 활동 신청 후 승인 여부·활동일 알림·실적 등록 안내 | 기관이 아닌 주민이 소규모 활동을 직접 개설 |
| VMS | 관리센터·인증관리요원이 모집·배치·실적 인증 관리 | 공식 인증 대신 체크인·완료 확인 기반 내부 기록 |
| 서울동행 청년 기획봉사단 | 청년이 프로젝트형 봉사를 기획·운영, 멘토링·실행 지원 | 기획 심사 없이 3시간 이내 활동을 바로 모집 |

| 본 작품 구현 계획 | 위치 검색 → 신청·승인 → 정원 잠금·대기열 → 체크인 → 완료 기록 | 참가 상태 전환을 서버가 규칙으로 검증 |

### 3.4 차별점이 드러나는 세 가지 기능

- **첫째, 가깝고 짧은 활동을 누구나 연다.** 활동을 2~10명·3시간 이내로 제한하고 좌표 기반 반경 검색을 제공해, ‘이번 주말, 우리 동네’처럼 좁은 조건에서도 활동을 찾을 수 있게 한다.
- **둘째, 정원과 순번을 서버가 끝까지 관리한다.** 마지막 한 자리에 여러 명이 동시에 신청해도 한 명만 확정되며, 취소가 생기면 대기 순번대로 제한시간 안에 수락을 받는다.
- **셋째, 참여를 현장에서 확인한다.** 60초마다 바뀌는 QR과 위치·시간을 함께 확인하고, 체크인한 사람만 완료 기록을 받는다.

## 4. 작품 목표

### 4.1 최소 구현 범위와 완료 기준

참가 흐름 6단계(그림): **활동 개설**(위험도 검사) → **주변 탐색**(반경·시간 필터) → **신청·승인**(중복 신청 차단) → **정원 확정**(잠금·대기열) → **현장 체크인**(QR+위치) → **완료·기록**(모집자 확인). 모집 단계 / 참가 단계 / 활동 단계로 묶인다.

본 작품은 활동 개설부터 완료·기록까지 참가 흐름 6단계를 최소 구현 범위로 한다. 각 단계는 기능이 동작하는 것에 그치지 않고, **규칙을 어기는 요청(정원 초과 승인, 시간 밖 체크인 등)을 서버가 막을 때 완료**로 본다.

### 4.2 시연 범위

학교 주변 공원·산책로 등 공공장소 3곳을 가상 활동 장소로 등록하고, 모집자 2명·참가자 6명·관리자 1명의 모의 계정을 사용한다. 위치 확인은 실제 휴대폰 위치와 브라우저 개발자 도구의 위치 변경 기능을 함께 사용해 반경 안/밖 상황을 재현한다. 핵심 시연은 아래 세 가지로 좁힌다.

| 시연 | 핵심 |
|---|---|
| 정상 흐름 | 활동 개설(LOW) → 반경 검색·신청 → 승인·확정 → QR+위치 체크인 → 완료 확인 → 활동 기록 |
| 정원·대기열 | 마지막 1자리에 2명 동시 신청 → 1명 확정·1명 대기 → 확정자 취소 → 대기자 승격 제안 → 시간 초과 시 다음 순번 |
| 안전 관리 | 금지 활동 게시 차단(BLOCKED) → REVIEW 활동 관리자 승인 → 활동 중 신고 → 기록 보류 → 조치 사유 기록 |

노쇼 누적 시 신청 제한, 봉사 크루 반복 활동을 추가로 기획한다.

### 4.3 제외 기능과 우선순위

1365 실적 연계, 실시간 채팅, 앱 푸시 알림, AI 자동 판정, 후원·결제 기능은 제외한다. 알림은 화면 안 알림 목록을 주기적으로 조회하는 방식으로, 추천은 거리·시간·관심분야 점수를 더하는 단순한 방식으로 대신한다.

일정이 부족하면 추천·지도 표현·크루를 줄이나, 권한 검증, 위험도 검사, 정원 잠금, 대기열 승격, 체크인 검증, 완료 기록, 신고 처리 규칙은 유지한다.

## 5. 실용적 근거

### 5.1 사용자에게 제공할 효용

- **맞는 시간대의 활동을 직접 만든다:** 탐색 단계 미참여 이유 1위는 ‘참여할 수 있는 시간대의 활동이 없어서’(47.8%)였다. Volink에서는 참가자도 모집자가 되어 원하는 시간에 활동을 열 수 있다.
- **짧은 활동만 모은다:** ‘시간이 오래 걸리는 활동밖에 없어서’(21.2%)라는 응답에 맞춰 활동 시간을 3시간 이내로 제한한다.
- **하고 싶은 사람을 실제 참여로 잇는다:** 20~24세의 참여 의향(29.3%)은 실제 참여(12.1%)의 약 2.4배다. 가까운 활동을 몇 번의 클릭으로 신청하게 해 이 차이를 줄이는 것을 목표로 한다.
- **모임이 있어야 움직인다:** 참여 이유 1위는 소속 조직의 단체활동 동참(35.0%)이다. 개인이 연 활동과 크루가 이 ‘모임’ 역할을 한다.

### 5.2 참가자와 모집자의 참여 방안

참가자와 모집자 모두 참여할 이유가 있어야 활동이 성립한다. 참가자에게는 가까운 곳에서 짧게, 연락처 공개 없이 참여할 수 있다는 점을, 모집자에게는 확정·대기·출석 관리를 서버가 대신 해준다는 점을 제공한다.

### 5.3 사용성 검증 계획

| 검증 과제 | 측정 항목 | 목표 |
|---|---|---|
| 활동 개설 | 완료율·소요 시간·누락 항목 | 80% 이상이 도움 없이 5분 안에 완료 |
| 주변 활동 찾기·신청 | 반경·날짜 조건 설정 성공, 소요 시간 | 80% 이상이 3분 안에 원하는 활동 신청 |
| 대기·승격 이해 | 대기 순번·응답 제한시간 설명 가능 여부 | 80% 이상이 화면만 보고 설명 |
| 현장 체크인 | 체크인 소요 시간, 실패 시 대처 | 80% 이상이 1분 안에 완료 |
| 완료 기록 확인 | 기록·이의 제기 위치 찾기 | 80% 이상이 도움 없이 찾음 |
| 규칙 위반 요청 | 정원 초과·시간 밖 체크인·무권한 접근 | 필수 서버 검증 시나리오 전부 통과 |

사용자 평가는 자발적 참여자 6~8명을 목표로 한다. 비율과 함께 실제 성공 인원, 소요 시간 중앙값, 실패 이유를 기록한다. 위 수치는 개발 목표이며 평가 결과가 아니다.

### 5.4 운영상 한계

체크인은 참여 사실을 완벽하게 증명하지 않는다. QR 화면을 다른 사람에게 전달하거나 기기 위치를 조작하는 경우를 모두 막을 수는 없으므로, 시간·QR·위치를 함께 확인해 부정 가능성을 줄이는 수준으로 설계한다. 활동 기록은 플랫폼 내부 참여기록이며 공식 봉사실적이나 법적 증명으로 사용하지 않는다.

Volink 활동은 자원봉사 종합보험 적용 대상이 아니다. 그래서 위험 활동을 게시 전에 차단하고, 모집자 안전 체크와 보험 비적용 안내를 반드시 거치게 한다. 사고가 나면 119 신고 등 공적 대응을 먼저 안내하며, 플랫폼은 사고 책임을 판정하지 않는다.

관리자는 모집글 삭제, 기록 무효, 활동 제한, 계정 정지 같은 플랫폼 내부 조치만 한다. 범죄 여부나 손해배상 같은 법적 판단은 하지 않으며, 수사기관 요청에 대비해 신고·처리 기록을 보관한다.

## 6. 기술 분석

### 6.1 시스템 구성

참가자·모집자·관리자는 같은 반응형 웹 서비스를 사용하고, Spring Boot 서버가 인증·정원·대기열·체크인·위험도 검사 규칙을 처리한다. 활동·참가 데이터는 MySQL에, 활동 사진과 신고 증빙은 비공개 파일 저장소(Amazon S3)에 보관한다. 지도 표시는 브라우저에서 Kakao 지도 API를 불러와 처리하고, 거리 계산과 반경 검색은 서버와 DB에서 처리한다.

### 6.2 핵심 처리 방식

**① 정원 확정(중복·초과 방지)** — 신청 승인은 하나의 트랜잭션으로 처리한다. 해당 활동 행을 잠근 상태(`SELECT … FOR UPDATE`)에서 확정 인원을 다시 세고, 정원보다 적을 때만 확정한다. 같은 사람이 같은 활동에 두 번 신청하지 못하도록 `(activity_id, user_id)`에 중복 금지 제약을 건다. 화면이 보낸 인원 수는 신뢰하지 않는다.

**② 대기열 승격(응답 제한시간)** — 확정자가 취소하면 같은 트랜잭션에서 대기 1순위를 ‘승격 제안’ 상태로 바꾸고 응답 마감 시각을 저장한다. 응답 제한시간은 활동 시작까지 24시간 이상 남았으면 6시간, 그보다 가까우면 1시간이다. 스케줄러가 1분마다 마감이 지난 제안을 만료 처리하고 다음 순번에게 넘기며, 활동 시작 2시간 전에는 대기열을 마감한다.

**③ 체크인 검증(시간·QR·위치)** — 모집자 화면의 QR에는 활동 번호와 발급 시각을 서버 비밀키로 서명한 값을 담고 60초마다 새로 발급한다. 서버는 서명·유효시간·체크인 허용 시간(시작 30분 전~시작 후 30분)을 확인한 뒤, 참가자 브라우저가 보낸 좌표와 활동 장소 사이의 거리가 200m 이내인지 계산한다. 위치 권한을 거부했거나 반경 밖이면 모집자가 수동으로 확인할 수 있지만, 사유 입력을 필수로 한다.

**④ 완료와 노쇼** — 활동 종료 후 모집자는 체크인한 참가자만 완료 처리할 수 있다. 체크인 없이 종료된 확정자는 스케줄러가 노쇼로 기록한다. 모든 상태 변경은 변경 전후 상태·처리자·사유와 함께 상태 변경 기록(ACTIVITY_LOGS)에 남긴다.

### 6.3 위치 정보와 개인정보 처리

참가자의 현재 위치는 검색과 체크인 순간에만 사용하고 좌표 자체는 저장하지 않는다. 체크인에는 반경 안/밖 결과와 시각만 남긴다. 활동 장소는 공공장소만 등록하도록 안내하고, 모집자 개인 주소가 드러나는 장소는 검토 대상으로 한다.

연락처는 다른 사용자에게 공개하지 않으며, 신청·확정·변경 안내는 플랫폼 알림으로만 전달한다. 로그인 역할뿐 아니라 활동·신청의 소유관계를 확인해 자기 활동의 신청자 목록만 볼 수 있게 한다. 업로드 파일은 크기·확장자·실제 형식을 검사하고 사진 속 위치 정보 등 메타데이터를 제거한 뒤 비공개로 저장하며, 열람할 때만 제한시간 URL을 발급한다. 법정대리인 동의 절차는 구현하지 않으므로 **만 14세 미만은 가입할 수 없게** 한다.

### 6.4 위치 기반 검색과 추천

활동 장소는 MySQL의 POINT 자료형(좌표계 SRID 4326)으로 저장하고 공간 인덱스를 건다. 검색은 두 단계로 한다. 먼저 검색 반경을 감싸는 사각형 범위로 인덱스를 이용해 후보를 빠르게 추리고, 다음으로 `ST_Distance_Sphere` 함수로 실제 거리를 계산해 반경 밖 활동을 빼고 가까운 순으로 정렬한다.

| 사용자 기준 거리 | 활동 | 1단계: 사각형 후보 | 2단계: 3km 거리 계산 |
|---|---|---|---|
| 0.8km | 활동 A | 포함 | 표시 |
| 1.6km | 활동 B | 포함 | 표시 |
| 2.9km (대각선 방향) | 활동 C | 포함 | 표시 |
| 3.4km (사각형 모서리) | 활동 D | 포함 | 제외 |
| 4.2km | 활동 E | 제외 | 제외 |

### 6.5 참가 상태와 대기열 규칙

| 상태 전환 | 전환 조건 |
|---|---|
| 신청 → 참가 확정 | 모집자 승인, 활동 행 잠금 후 확정 인원 < 정원 |
| 신청 → 대기 | 정원이 찬 상태에서 신청, 신청 순서대로 순번 부여 |
| 대기 → 승격 제안 → 확정 | 빈자리 발생 시 1순위에게 제안, 제한시간 안에 수락 |
| 승격 제안 → 만료(다음 순번) | 제한시간(6시간/1시간) 초과, 활동 시작 2시간 전 대기열 마감 |
| 참가 확정 → 취소 | 활동 시작 전 본인 취소, 빈자리는 즉시 승격 처리 |
| 참가 확정 → 체크인 | 시간·QR·위치 검증 통과, 또는 사유가 있는 모집자 수동 확인 |
| 참가 확정 → 노쇼 | 체크인 없이 활동 종료 |
| 체크인 → 완료 | 활동 종료 후 모집자 완료 확인, 활동 기록 생성 |
| 진행 중 → 보류 → 재개/무효 | 신고 접수 시 보류, 관리자가 사유 기록 후 재개 또는 기록 무효 |

### 6.6 데이터 구조와 ERD

계획서 ERD 그림: **16개 테이블**, IE 표기법, 네 묶음(색 구분).

| 묶음 | 테이블 · 주요 컬럼 |
|---|---|
| ① 사용자·분류 | `USERS`(user_id, email UK, password_hash, nickname, role USER·ADMIN, status 정상·제한·정지) · `USER_INTERESTS`(user_id, category_id, 복합 PK) · `CATEGORIES`(category_id, name, base_risk LOW·REVIEW) · `NOTIFICATIONS`(notification_id, user_id, type 확정·승격·변경, read_at) |
| ② 활동 | `ACTIVITIES`(activity_id, host_id→USERS 모집자, category_id, start_at·end_at, capacity 2~10, risk_level·status) · `ACTIVITY_LOCATIONS`(activity_id 1:1, place_name, point POINT 4326, checkin_radius_m 200) · `CREWS`(crew_id, leader_id, name, 선택) · `CREW_MEMBERS`(crew_id, user_id, joined_at, 선택) |
| ③ 참가 | `APPLICATIONS`(application_id, user_id, activity_id, UQ(activity_id,user_id), status 신청·확정·대기…, wait_no·offer_expires_at) · `ATTENDANCE`(attendance_id, application_id UQ, method QR·수동, in_radius·checked_at) · `COMPLETIONS`(completion_id, application_id UQ, host_confirmed_at, dispute_until·voided) · `ACTIVITY_LOGS`(log_id, activity_id, application_id nullable, from→to_status, actor·reason) |
| ④ 안전·관리 | `REPORTS`(report_id, reporter_id, activity_id, type·status) · `REPORT_FILES`(file_id, report_id, object_key S3) · `SANCTIONS`(sanction_id, user_id, report_id, type·until_at) · `ADMIN_ACTIONS`(action_id, admin_id, target_type·id, action·reason) |

점선 관계(CREWS·CREW_MEMBERS)는 일정 여유 시 구현하는 선택 항목이다.

ERD는 참가 흐름 순서에 따라 네 묶음으로 나뉜다.

1. **사용자와 분류:** 누가 서비스를 쓰는지, 어떤 분야에 관심이 있는지 저장한다. 관리자 역할은 가입 시 선택할 수 없다.
2. **활동:** 모집자가 연 활동과 장소 좌표를 저장한다. 장소는 활동과 1:1이며 공간 인덱스를 둔다.
3. **참가:** 신청 1건이 확정·대기·체크인·완료까지 상태를 바꾸며 진행한다. 체크인과 완료는 신청 1건당 1건만 생기고, 모든 전환은 상태 변경 기록에 남는다.
4. **안전·관리:** 신고와 증빙, 회원 제재, 관리자 처리 기록을 저장한다.

**데이터 규칙**

- 한 사람은 같은 활동에 신청을 1건만 할 수 있다. (중복 신청 방지)
- 확정 인원은 정원을 넘을 수 없다. (활동 행 잠금 후 재확인)
- 체크인 기록이 없는 신청은 완료 처리할 수 없다.
- REVIEW 활동은 관리자 승인 전까지 검색되지 않고, BLOCKED 활동은 게시되지 않는다.
- 관리자 조치와 수동 체크인은 사유 없이 저장되지 않는다.

### 6.7 위험 대응과 보안 기준

| 등급 | 의미 | 예시 | 처리 |
|---|---|---|---|
| LOW | 공공장소·주간·단순 활동 | 플로깅, 공원 환경정화, 불법전단 제거 | 즉시 게시 |
| REVIEW | 대상자·장소 확인이 필요한 활동 | 어르신·아동 대상 활동, 동물 관련 활동, 시설 내부 활동, 일몰 이후 종료 | 관리자 검토 후 게시 |
| BLOCKED | 플랫폼에서 허용하지 않는 활동 | 의료행위, 전기·가스 작업, 높은 곳 작업, 물속 작업, 금전 모금 | 게시 차단 |

위험도 검사는 명확한 금지 규칙 → 위험 키워드 → REVIEW 항목 관리자 최종 확인 순서로 진행한다. 키워드 검사는 위험 가능성을 골라내는 보조 수단이며 활동의 안전성을 보증하지 않는다. 비밀번호는 단방향 해시로 저장하고, 로그에는 비밀번호·인증 토큰·좌표 원문을 남기지 않는다.

## 7. 구현 환경

### 7.1 개발 도구

## 8. 추진 일정

### 8.1 개발 일정과 마일스톤

개발 기간은 2026년 9월 29일부터 11월 23일까지 약 8주다. 3~4주 차에 서버를 먼저 배포하고, 6주 차까지 개설 → 신청 → 체크인 → 완료의 기본 흐름을 연결한다. 7주 차에는 예외 처리·사용성 평가, 8주 차에는 통합 검증·발표를 진행한다. 수업 일정과 요구사항에 따라 조정될 수 있다.

역할별 개발 일정(간트차트 그림, 2주 단위 막대):

| 주차 | 오준원 | 박용빈 | 김병수 |
|---|---|---|---|
| 1~2주 | 화면 흐름·UI 시안(지도·목록) | 명세·ERD·권한·상태 전이 설계 | 시연 장소·계정 데이터, 위험 키워드 |
| 3~4주 | 활동 개설·주변 탐색 화면 | 인증·활동·위치검색 API, 첫 배포 | 검증 시나리오별 테스트 케이스 |
| 5~6주 | 신청·대기열·체크인 화면 | 신청·정원 잠금·대기열·체크인 API | API·규칙 테스트(동시 신청 포함) |
| 7~8주 | 완료·마이페이지·관리자 화면·발표 | 완료·신고·관리자 API, 운영 점검 | 사용성 평가·시연 준비 |

공동: 매주 금요일 통합·상호 코드 검토·기능별 테스트. ◆ 4주 말 첫 배포 완료 → ◆ 6주 말 기본 흐름 연결(개설→신청→체크인→완료) → ◆ 8주 말 최종 시연.

## 첨부 · 구현 예상 화면 (그림 내용 요약)

계획서 그림의 서비스 이름은 시안용 표기이며, 실제 서비스명은 Volink입니다. 이름·주소·사람 표시는 모두 예시입니다.

1. **활동 개설과 위험도 검사(모집자)** — 활동명·일시·장소·정원을 입력하면 서버가 위험도를 검사해 LOW·REVIEW·BLOCKED 결과를 보여준다. 4단계(기본 정보 → 일정·장소 → 모집 설정 → 안전 확인). 오른쪽에 위험도 자동 검사 결과(공공장소·주간·3시간 이내·금지 키워드 없음·정원 10명 이하)와 모집자 안전 체크 3개, 공식 실적·보험 비적용 안내. 지도에 집결 장소와 체크인 반경 200m 표시. ‘임시저장’·‘게시하기’ 버튼.
2. **주변 활동 탐색(참가자)** — 검색 반경(예: 3km)·날짜·분야를 고르면 가까운 순 목록과 지도 마커가 함께 바뀐다. 목록 카드에 거리·확정 인원·‘대기 신청 가능’ 상태. 지도에 내 위치와 반경 원. “내 위치는 검색에만 사용되고 저장되지 않습니다.”
3. **참가자/대기열 관리(모집자)** — 정원·참가 확정·승격 제안 중·대기 인원 요약, 신청 순 참가자 목록(이름 일부 가림), 대기열(1순위 승격 제안 남은 시간 표시), 상태 변경 기록. 승인 버튼은 확정 인원이 정원보다 적을 때만 눌리고 서버에서도 다시 확인.
4. **현장 체크인(모집자/참가자)** — 모집자 휴대폰의 QR은 60초마다 바뀐다. 참가자가 스캔하면 서버가 시간·QR·위치를 확인해 체크인을 확정하고, 하나라도 맞지 않으면 거부한다. 거부 예: 위치 350m → 거부·모집자 수동 확인 요청, 캡처한 지난 QR → 만료 코드로 거부, 시작 1시간 전 → 시간 밖으로 거부.
